## Who notices

Players notice nothing. The board still filters Coached runs with `coachedSql`, so no ranking,
chip or count moves. A submit now makes two database round trips instead of three. Every new row
records whether it was coached and the run's fingerprint, and `pnpm db:backfill-runs` fills the
same two columns on the rows that already exist. 5f2 turns the fingerprint into the copy guard and
reads `coached` from the column.

The next engineer inherits a `run_fingerprint` recipe tagged `pdfp1`, a store whose `insert`
returns the rank, and one decode per board row through `readStoredToken`.

## Implementation decisions

**Fingerprint inputs come from the replay.** `runFingerprint` takes the `DraftState` and
`CupResult` that `replay` (submit) or `replayAnyVersion` (backfill) returns. Starters and bench come
from `draft.lineup`, formation from `draft.lineup.formation`, Team Score from `cup.rating.score`,
the same value the row stores. The hash uses `node:crypto` in `src/leaderboard/server`, never in
`src/engine`. The literal hex in the tests was derived outside the code under test: a Python script
built the preimage from a JSON dump of each replay and hashed it with `hashlib`.

**Coached is computed once per submit.** `parseSubmission` already called `isCoached(token)` for
the coach-view check. It now keeps the result on the submission, and `handleSubmit` writes it
(Laziness Protocol: no second decode).

**Insert plus rank is one data-modifying CTE.** `WITH inserted AS (INSERT ... RETURNING *) SELECT
row_to_json(inserted), (SELECT count(*) FROM leaderboard_entries WHERE board AND coach AND
aheadOf(inserted))::int + 1 FROM inserted`. `aheadOf` now takes values or SQL references, so the
same tie-break order serves `rankOf` and the CTE. The outer query sees the table as it was before
the insert, and a row is never strictly ahead of itself, so the count is right. The drizzle insert
builder is embedded as is: drizzle wraps it in parentheses itself, and a second pair is a syntax
error (found on the first GREEN run, every submit returned 503). `rankOf` stays for the retry path
(`savedEntry`), as the hand-off says. `rowFromJson` now maps both the retry row and the inserted
row (one mapping instead of two).

**A rank failure can no longer follow a saved insert.** Dispatch 5 returned 201 with `rank: null`
when the separate rank query failed after a saved insert. With one statement, either the row is
saved and ranked, or nothing is saved and the submit returns 503, which is safe to resend. The
`rank: null` path remains for a retry whose `rankOf` fails. The two tests that covered it moved to
that path (see spec churn).

**The daily probe is built in JS.** `admitSubmission` emits `false` instead of the `EXISTS` clause
when `board.dailyDate` is null. The `dailyTaken` interface method and its implementation are
deleted. No test fake implemented it.

**One decode per board row.** `readStoredToken(token)` runs `decodeToken` once and derives both
the squad preview and the Coached chip (`MANAGER_TOKEN_VERSIONS` includes the version and the run
has at least one manager action). A token the live decoder rejects has no preview and falls back to
`isCoached`. `squadPreview` is deleted and its test calls `readStoredToken` (Migrate Callers Then
Delete Legacy APIs). One tamper-only token reads differently: a pd6 payload with an explicit empty
manager list is coached to `isCoached` and `coachedSql`, and not to the live decoder, which drops
the empty list. `encodeToken` never writes one, and submit stores only canonical re-encodes, so no
real row has it. A test pins it, the same way `coached-sql-hardening.md` pinned its three residual
payloads. 5f2 reads `row.coached` and removes the difference.

**The backfill refuses rather than guesses.** `backfillRuns` selects rows where either column is
NULL, replays each token with `replayAnyVersion`, and computes `coached` with `isCoached` and the
fingerprint. A row whose token does not replay, or whose stored W-D-L and Team Score differ from
its replay, refuses the whole run: it prints `refused id=<id> version=pd<n>: <reason>`, writes
nothing and exits 1. The record check is beyond the hand-off's letter. A fingerprint of a replay
that disagrees with the row would describe a run the row does not hold, which is fabricated data.
The updates run in one transaction and touch only the two columns, by `id`. The selected rows are
parsed with zod at the boundary. `--dry-run` prints each `id`, version and computed value and the
count. A second run selects 0 rows (Make Operations Idempotent). The logic lives in
`src/leaderboard/server/backfill.ts` behind a two-method port, so the PGlite test runs the exact
function the Neon script runs (Build the Lever).

**`db:smoke` writes the new columns.** It inserts `coached = false` and a `run_fingerprint`, and its
select reads them back. The two smoke rows use different fingerprints, so the daily-nickname 23505
stays the thing it proves, also after 5f2's unique index. The smoke now needs 0004 applied; the
3.6 order always runs it after `db:migrate`.

**Commit shape.** Each guard landed as a failing test commit followed by its fix (Sequence Work
into Verifiable Units). Two follow-ups touched a RED test after its GREEN: `d858a0d` typed the
swapped lineup in the slot-order test (a `tsc` error the RED commit carried; vitest does not type
check), and `81f2cb3` dropped a type argument from the PGlite port in `backfill.test.ts` when the
port started returning `unknown[]`.
