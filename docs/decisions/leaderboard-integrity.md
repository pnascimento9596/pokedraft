includes 5f1, #126). The row spec is hand-off section 4.3 "5f2 contract"; the database steps are

## Who notices

A player who submits a copy of a run that is already on the board gets a 409 and the message "This
exact run is already on the board, listed under Misty." A copy here means a token whose replay has
the same mode, seed, formation, squad slots, W-D-L, Team Score and goals as a listed run, for
example the same run with an extra touchline decision that changes nothing. Before this row such a
copy was listed a second time under a new nickname. Every other submit behaves as before.

The Coached filter and the Coached chip now read the stored `coached` column, so a row can no
longer sit in one view while its chip says the other.

The next engineer inherits two NOT NULL columns, a unique `(mode, run_fingerprint)` index, a
`listedRun` store method in place of `byToken`, and no SQL token parser.

## Product decisions applied

- Decision 5 (brief section 2): close the copy bypass. 5f2 is the contract half of 5f1's expand.
- Uniqueness is per `(mode, run_fingerprint)`, as the hand-off re-decided, not per `(mode,
  daily_date)`. The seed is already in the fingerprint, and a plain unique index treats the NULL
  `daily_date` of every all-time row as distinct, so the date form would let all-time copies in.
- **Decided tradeoff: honest identical Daily runs.** Two friends who draft the same XI in the same
  slots on the same Daily and get the same result have the same fingerprint. The second is refused
  and sees the first's nickname. The guard cannot tell this case from a copy, and the two runs would
  tie on every board column anyway. The message says why ("This exact run").

## Implementation decisions

**The no-op copy starts from a coached run (re-decided).** The hand-off's guard submits the plain
golden pd6 run as Misty, then a copy with two identical `attack` decisions. At this head any
manager decision switches the auto coach off for the rest of the match
(`src/engine/match.ts:560-575`, `managed = true`), so that copy is a different run. Measured on the
golden pd6 token: plain pd6 fingerprints `65b48b25...` and pd6 with `attack` at minute 0 fingerprints
`d3d86d21...`, both 5-0-1 and Team Score 593. Adding a second `attack` at minute 1 keeps
`d3d86d21...`, because a tactic equal to the current one records nothing
(`match.ts:563`). So Misty submits pd6 with `attack` at minute 0 and Brock submits it with
`attack` at minutes 0 and 1. That is the hand-off's first option ("append attack at minute 1 after
attack at minute 0"); the fixture simply needed the minute 0 decision first. A decision on an
unplayed match is no cheaper copy: replay refuses it with "a coach decision names a match the run
never played".

**`listedRun` replaces `byToken`.** After an insert conflict the handler needs the row that holds
the run, by token for a concurrent retry and by fingerprint for a copy. One query covers both with
an `OR`. A retry is answered with 200 only when the listed row has the same token and nickname; a
same-nickname copy with another token gets 409 naming the player's own row, which is honest.

**The admission conflict names the nickname too.** A same-token copy is caught at admission, before
the replay, and the admission query already returns the existing row. Its `nickname` goes into the
409, so both copy paths read the same.

**Constraint names map through a `Map`.** An unknown 23505 constraint stays a `token` conflict, as
before. A `Map` keeps a constraint name such as `constructor` from resolving to an object property.

**The index uses `DESC` (NULLS FIRST), not drizzle's default `DESC NULLS LAST`.** The board query
orders `wins desc, draws desc, team_score desc`, which is NULLS FIRST, and the hand-off names plain
`DESC`. The schema writes `.desc().nullsFirst()`. PGlite `EXPLAIN` with `enable_seqscan = off` on
the coached all-time top-50 query shows `Index Scan using leaderboard_entries_coached_board_idx`
with `Presorted Key: wins, draws, team_score, created_at`.

**The backfill is deleted.** NOT NULL makes `WHERE coached IS NULL OR run_fingerprint IS NULL`
empty forever, and production already ran it (precondition). If 0005 is rolled back the deployed
code still writes both columns, so no NULL can appear. Its test inserted NULL rows, which 0005 now
refuses. The replacement guard is the 0005 migration test, which asserts a NULL in either column is
refused with 23502. Principles: subtract before you add, outcome-oriented execution (the expand
phase's tool goes with the contract).

**The parity tests are replaced, not ported.** `coach-board.test.ts`'s `coachedSql` vs `isCoached`
tests and `coached-sql.test.ts` tested a rule that no longer exists. The replacements are "files a
row by its coached column, not by its token" (RED) and "stores coached equal to isCoached(token)
for every fixture token a submit accepts" (regression guard).

**5f1 carryover 1 closed.** The empty manager list token is coached for `isCoached` and was not
for the live decoder. The chip and the filter now both read `row.coached`, which submit writes from
`isCoached`. The pin in `board-entry.test.ts` now asserts `[true, true]`.

**The migration is safe for the live 5f1 code.** The 5f1 code writes both columns, and it maps any
unknown 23505 constraint to `DUPLICATE_TOKEN`. Proof: the RED `handlers.test.ts` run against the
5f1 code at `3b821d1` with migration 0005 added (a throwaway worktree) gave the copy
`[409, 'DUPLICATE_TOKEN', undefined]`, so the live site refuses copies as soon as 0005 runs, without
the nickname. The only other failures there were three tests whose fixtures insert rows without the
two columns (23502), which no live code path does.
